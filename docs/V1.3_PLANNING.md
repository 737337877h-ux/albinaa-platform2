## Risks

1. **Push (FCM/APNS):** اعتماديات جديدة + حساب FCM/APNS + EAS projectId + تحديث mobile + كشف أجهزة — أعلى مخاطر تكامل ويُطيل أفق الإصدار. الموبايل حاليًا polling محلي؛ نقله لـPush تغيير معماري.
2. **المحور 6 (Reservations):** نماذج خاملة بمعنى مغاير ("حجوزات أصناف/أرصدة") — إعادة استخدامها كما هي دون مراجعة خطر تصميم خاطئ؛ التصميم يجب أن يُعرّف الحقول المطلوبة صراحة.
3. **`summary` يعيد قيم null قديمة** — أي شاشة/رسم جديد لا يجب أن يعتمد عليها؛ الاعتماد على `kpis` والسجلات الزمنية.
4. **Bug قائم:** reset-password UI يرسل `password` بدل `newPassword` — سيُكشف كفشل فور استخدامه؛ يُصلح ضمن أول PR يمس صفحة الإدارة.
5. **تغيير username:** قد يكسر مراجع خارجية/جلسات — يتطلب audit + إبطال جلسات + معالجة تفرد `(org, username)`.
6. **صلاحيات على مستوى المستخدم:** سطح إدارة أوسع وصعب التدقيق — يُنصح بالبقاء على الأدوار.
7. **Data Quality:** مراجعة بشرية فقط — خطر زحف النطاق نحو دمج/حذف تلقائي (ممنوع بتصميم).
8. **الرسوم:** لا مكتبة رسوم حاليًا — إما اعتمادية جديدة (تنافي ثقافة "بلا dependencies") أو رسوم SVG محلية خفيفة (الموصى به).
9. **توزيع المهام الجماعي** يشمل معايير بالغة (رصيد/مخاطر) — يحتاج حدودًا واضحة لتجنب توزيع خاطئ؛ قواعد تحقق قبل أي كتابة (مثل نمط الوعود).

## Recommended v1.3 scope

- **داخل النطاق:** المحاور **1–6 كاملة** + المحور 7 **للأنواع in-app فقط** (`task_assigned` + `followup_due`).
- **بدون migration إلا محور واحد:** محور 6 (حجوزات البضاعة) فقط.
- **بلا اعتماديات جديدة:** رسوم SVG محلية.
- **نظام الأدوار يُبقى القاعدة:** لا صلاحيات على مستوى المستخدم في هذه المرحلة.
- **الموبايل لا يتغير** (إشعارات in-app تُعرض في الويب؛ الموبايل سيقرأ الأنواع الجديدة بلا تعديل كود — أو تحديث خريطة الأنواع فقط إن لزم).

## What should be postponed

- **Push notifications (FCM/APNS)** → إصدار لاحق (يتطلب اعتماديات جديدة + حساب FCM/APNS + تغيير معماري في الموبايل + جدول device tokens).
- **الدمج/الحذف التلقائي للعملاء** → ممنوع بتصميم؛ مراجعة بشرية فقط دائمًا.
- **صلاحيات على مستوى المستخدم** → اختيارية لاحقًا (جدول `UserPermission`).
- **تحويل الحجوزات إلى تحصيل/فاتورة أو تأثيرها على الرصيد المالي** → مرحلة لاحقة مستقلة.
- **تحديث Mobile App** → فقط عند الدخول في الـPush.

## Final recommendation

1. اعتماد النطاق الموصى به أعلاه (المحاور 1–6 + أنوية إشعار in-app).
2. التنفيذ عبر PRs منفصلة بالترتيب المقترح (A→G)، كل PR بوحدات + e2e، مع إصلاح bug إعادة تعيين كلمة المرور أولًا.
3. الغاء أي schema/migration إلا محور 6 (وحذف الـPush من النطاق الافتراضي).
4. بعد اعتماد هذا التقرير، يُحدَّد أول PR تنفيذي ويُفتح من فرع ميزة مستقل — لا يُنفَّذ أي كود قبل ذلك القرار.
